# 首关卡顿优化 · 2026-09-28

**当前实现与用户提出的 Draw Call < 50 / 稳定 60 FPS 验收状态见 [移动与绘制优化](movement-performance.md)。下文保留早期试验记录；当前玩家 / 弹道为 60 Hz，NPC 分帧 30 Hz，不能把早期整体 30 Hz 的说明当作当前设置。**

后续弹壳 / 弹匣休眠、MultiMesh 实例合批与固定物件分区烘焙见 [合批记录与基准](fx-and-prop-batching.md)。

用户反馈实际试玩严重卡顿。本次对同一个 Godot 首关优化；保留双方兵力、胜负、武器、原骨架、真实坡沟与墙体破坏。没有追加自动对局，也未自动操控用户的游戏窗口。

## 已定位的成本

此前三轮日志已经证明纯世界逻辑有长帧：第三轮前 60 秒 CPU 单步中位 36.87 ms、P95 52.02 ms，峰值单位逻辑超过 100 ms。游戏实际物理频率为 60 Hz，每步预算约 16.67 ms；超预算的逻辑会挤占画面更新。此次冻结首关进一步定位到：

- 地形射线逐个穿越 0.5 m 格，并在明显高于地表时仍构造两个三角面求交。
- 长斜射线查询整个矩形内的障碍，命中建筑包围盒后又检查整面墙的全部破坏格；人物移动反复检索相同空间格，车辆碰撞描述也反复更新。
- 60 名角色每个画面帧都重新采样原动画、计算骨骼与握枪姿势；屏外角色同样执行。死亡动画结束后仍重复采样终帧。
- 原步兵重叠脱困最多一次扫描 20 圈 × 16 个候选，并为可选点多次检查整段逃离路径。多名 AI 同时受阻会形成集中搜索尖峰。

原项目参考是 `server/GrandBattleSimulation.mjs` 的沿线空间格查询，以及 `server/StreetNavigation.mjs` / `LayaTacticalAdvisor.mjs` 的复用与错峰计算方式。三维版本仍以真实地形、骨骼和破坏状态计算。

## 修改

1. 地形增加 4 m 分块的保守最高点索引。射线完全高于该块时跳过，否则仍进入原 0.5 m 格与原三角面精确求交。高度与坡度直接按同一三角面的三个顶点计算，减少临时数组。
2. 障碍射线沿穿过的空间格查询；墙体只检查射线在墙内穿过的行列。局部候选复用固定空间格结果，索引重建时清理缓存；HP、存活状态与破口仍实时检查。
3. 载具碰撞盒按车身位置、角度和炮塔角度更新；离查询位置很远的载具先通过保守包围框排除。
4. 玩家姿势逐帧更新；普通 AI 在视野附近以 30 Hz、屏外以 8 Hz 错峰更新骨骼。角色位置与身体命中胶囊随每帧移动，开火时仍求当前实际枪口，翻越、梯子和固定武器操作保持完整更新。新生命清空的命中形状立即重建。
5. 死亡动画播完后保留精确终姿，落地与支撑仍检查。AI 脱困沿原候选顺序分帧继续，每个单位一次最多 12 个候选，共享约 2 ms 搜索预算；完整的单个候选检查可能略越预算，不是硬实时保证。翻越路径、速度与碰撞参数保持原值。
6. 增加 `--performance-log`：只观察用户操作，每五秒记录实际 FPS、物理步骤、画面更新耗时、在场人数及弹丸数，输出到 Godot 当前日志。

## 验收窗口暴露的调度问题与追加修复

第一版优化窗口打开后进入了战斗。`qa/performance/user-play-60hz.log` 记录了 30–60 模拟秒的实际窗口数据：物理步骤中位约 15.5–18.2 ms，仍每秒执行约 60 次；每五秒只有约 38 次画面更新，却执行约 304 次物理步骤，几乎每个画面帧都补做八步，实测只有 5–7 FPS。**单个查询更快并不等于整场流畅；这份失败记录保留。**

据此将正式首关战斗逻辑设为原版使用的 30 Hz，每个画面帧最多补两步；画面、鼠标准心和相机仍独立更新。返回训练场恢复原 60 Hz / 八步上限。新增 139 项纯步长检查通过：全部武器模式的 30/60 Hz 触发时钟在十秒内相差至多一发，走跑距离差小于 0.15 m、跳跃峰值差小于 0.075 m，均正常落地。这些是隔离数学检查，不创建战斗或弹丸。

最终 30 Hz 版本已重新打开，日志 `qa/performance/level01-live-30hz.log` 确认 `physics_hz=30`、暂停时 `simulation_time=0`，包含角色、屋顶、弹丸外观与 FX 的分段耗时。最终持续交火 FPS 尚待用户再次开始；暂停 60 FPS 不能作为交火性能结论。30 Hz 意味着输入进入战斗逻辑的步长为 33.3 ms，手感也需用户确认。

## 固定工作量的前后对比

以下全部是冻结场景的 CPU 基准；时间与射击计数保持零，不含模型请求，不是第四轮对局，也不是 GPU 帧率。

| 工作量 | 优化前中位 | 优化后中位 | 降低 |
| --- | ---: | ---: | ---: |
| 同一组 240 条地形射线 | 46.281 ms | 1.603 ms | 96.5% |
| 同一组 240 条完整遮挡射线 | 82.642 ms | 14.076 ms | 83.0% |
| 60 人 × 4 处移动/支撑/地表查询 | 22.318 ms | 14.314 ms | 35.9% |
| 59 名 AI 的一批感知查询 | 29.457 ms | 7.810 ms | 73.5% |
| 冻结 60 人的客户端画面更新 | 9.286 ms | 4.386 ms | 52.8% |

几何基准各预热一次、测量七次；画面基准 16 次调用、剔除前两次。画面基准的“优化前”在几何优化后采集，用于单独衡量姿势调度的额外收益，不能与几何耗时相加推算最终 FPS。姿势调度后的画面更新时间最大值为 5.050 ms，前值 10.431 ms。原始数据保存在 `qa/performance/*-hotpaths.json` 和 `*-views.json`。

## 校验与验收

- 7201 项新旧几何结果对照通过：随机与轴向/竖向射线、不同弹丸半径、地形高度/坡度、支撑/碰撞、实时破坏格及移动车体；命中距离误差阈值 0.2 mm。
- 12 项执行/表现检查通过：姿势降频后命中胶囊位置、枪口刷新后的重复平移防护、原肢体形状、死亡终姿休眠、脱困分帧与同侧退出、新生命清理。
- 原地貌回归 61 项、首关导航 248 项、统一场景入口/生命周期 38 项通过，覆盖关卡与训练场频率切换。

这些检查证明优化后的查询结果与基础行为保持一致。持续多人交火的最终帧率、GPU 负载与手感仍需用户试玩。本次启动同一 `res://proving_ground.tscn --level01 --briefing --performance-log`，先暂停等待用户，最终日志为 `qa/performance/level01-live-30hz.log`。

联合演武场及首关默认显示性能面板，**F4** 显示 / 隐藏。战况文字随面板让位；鼠标穿透面板，不影响瞄准与射击。每 0.25 秒刷新文本，隐藏时停止采样，不遍历场景、不启动外部内存查询进程。

- FPS、主循环 / 物理耗时、Draw Call、图元、绘制对象、显存、纹理 / 缓冲显存、引擎分配运存与峰值、节点 / 资源数直接读取 Godot `Performance`，与编辑器监视器同源。
- 帧间隔 / 最慢帧用单调时钟记录最近一次刷新区间内实际画面回调间隔；不使用可能被引擎限制的模拟 `delta` 推算。
- “三角面 / 图元”保留引擎原始计数，包含多次绘制，不是场景里唯一三角形数量。显存为引擎跟踪的资源占用，运存为引擎分配统计，不等于 Windows 进程工作集或整张显卡总占用。未提供的显存项和发行版不可用的运存项明确显示为未提供。
- 部分原生统计每秒更新一次；暂停时仍刷新，但暂停读数不代表实际交战性能。

数据口径参考 [Godot 4.6 Performance 文档](https://docs.godotengine.org/en/4.6/classes/class_performance.html)。启动参数 `--startup-watch` 会记录一次 `PERFORMANCE_OVERLAY_READY`，便于确认实际窗口已显示且统计有值。本次只做脚本编译与首关暂停启动检查，不额外自动对战。

## Laya 资源占用与解耦

2026-09-28 用户要求先解除 Laya 依赖。读取用户实际交战日志及 Windows / NVIDIA 计数，未自动操控游戏：

- Laya CUDA 进程 PID 28460，父进程 10120 是 Python 虚拟环境启动器，并非第二份模型。模型专用显存 1,981,292,544 字节（约 1.85 GiB）；实际工作集约 722 MiB，私有提交量约 3.40 GiB，两者不能混称为实际运存。
- 一次五秒采样中，Laya 平均约占单核 CPU 的 18.4%，首关 Godot 约 99.3%。当时还有独立的载具验收窗口约占单核 43.3%；该窗口保留，因而这不是隔离整机基准。
- 首关交战日志记录约 13–23 FPS 的片段，物理步骤中位约 20–22 ms；单次采样里的单位逻辑约 15–21 ms，弹丸 / 载具约 1–11 ms，客户端画面更新中位约 9–11 ms。指挥层单次采样通常很小，也有约 1.9 ms 的任务分配帧；这是整个指挥层时间，不能直接归为纯模型耗时。模型通过非阻塞 HTTP 连接独立进程，没有主线程等待推理。

结论：Laya 有明显资源占用，值得先移出性能基线；现有证据仍指向游戏 CPU 热点，不能承诺停用模型即可消除卡顿。停服务前后两秒内，整卡显存由 4272 MiB 降至 2267 MiB；该差值包含其他程序的同期波动。已确认模型进程与 8765 监听全部退出，模型文件保留。

默认本地模式不加载指挥通信模块、不创建连接、不发送观察或请求。规则小队编成、任务分配及底层 AI 保留；切回本地会取消队列并清除模型旧战术。可选恢复方式见首关说明。五秒性能日志新增 `ai_mode`、`laya_requests`、`laya_responses`、`laya_pending`，便于核实实际模式。

证据：`qa/performance/laya-resources-before.json`、`laya-resources-after.json`、`laya-enabled-user-play.log`；本地版窗口日志为 `level01-local-ai.log`。120 项指挥器检查通过，覆盖本地任务、默认零模型请求、显式启用、关闭优先、队列释放及旧回复隔离；只检查冻结状态，没有增加对局。关闭模型后的持续交火 FPS 留给用户在同一首关中对比。
