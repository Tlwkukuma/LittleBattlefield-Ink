# v32 实战卡顿分析

**结论：现有日志已确认，多人世界模拟占用大量主线程时间，独立动作/特效/HUD 又叠加在后；掉帧时同一显示帧内执行多次物理更新，使低帧率持续。动作预算随显示帧率下降，还可能额外造成肢体动画跳动。仅降低 Draw Call 不足以解决。**

本轮分析 v2026.09.28.32、2026-09-28 14:21:02、PID 19124 的用户实战记录。没有自动操作游戏。原运行窗口未重启、运行代码未修改；新增的仅是诊断脚本、分析结果和本记录。

## 2. 持续低 FPS：CPU 每帧预算已超支

最差窗口单次物理更新 P50 **10.04 ms**、P95 **13.72 ms**。该“物理”计时实际覆盖 `proving_world.gd.step()` 的自定义世界模拟：AI、移动、射击、弹道、载具和规则，不等于 Godot 刚体物理服务器单独耗时。

| 阶段 | 最差窗口 P50 | 最差窗口 P95 | 计量边界 |
| --- | ---: | ---: | --- |
| 世界模拟总计 | 10.04 ms | 13.72 ms | 每次物理更新 |
| 单位循环 | 6.51 ms | 8.64 ms | 世界模拟内部，不再与总计相加 |
| 其中移动/避让 | 2.59 ms | 2.80 ms | 单位循环内部 |
| 弹道及载具阶段 | 2.85 ms | 5.49 ms | 世界模拟内部 |
| 主场景画面回调 | 3.91 ms | 4.53 ms | 每个显示帧；不包含以下独立节点回调 |
| 特效回调 | 3.37 ms | 5.68 ms | 独立 `_process` |
| HUD 合批回调 | 1.35 ms | 2.24 ms | 独立 `_process` |
| 角色骨骼图集/实例上传 | 1.04 ms | 1.19 ms | 独立 `_process` |

各阶段分位数并非同一帧，不能直接相加当作精确总帧耗时。但即使按一次物理更新估算，主要工作已接近或超出 16.67 ms，还没有算齐其他批次、Canvas 绘制、引擎处理和 GPU 提交/等待。

这个窗口产生 **274 次物理更新、141 个显示帧，即平均每帧 1.94 次物理更新**。因此不能把面板里的“物理 10 ms”理解成这一帧只做了 10 ms 物理。物理时钟继续推进，显示变慢后会合并更多物理步到一帧里；这会放大单帧耗时。不是把物理上限改成 1 就能无代价解决，否则会影响模拟速度。[Godot Engine 固定时步说明](https://docs.godotengine.org/en/4.6/classes/class_engine.html#class-engine-property-max-physics-steps-per-frame)

当前已存在 NPC 30 Hz 交错更新与部分 AI 1 ms 预算，继续简单添加一次“降频”不是完整方案。预算主要约束感知刷新/寻路/掩体搜索，未覆盖移动、开火确认、命中查询和全部事件工作。

## 3. 最明确的算法热点：弹道未复用人物空间索引

`scripts/proving_world.gd:630` 的 `trace_3d()` 对静态物体已有网格筛选，但人体部分仍 `for u in units`，每条弹道遍历全部人物，再做阵营、包围盒和胶囊检查。世界更新在弹道前还关闭了避让用途的 `unit_grid_active`；现有索引没有用于人体射线。

新增 `qa/trace_resource_cost.gd` 在冻结的原入口场景执行纯射线数学检查，包含 60 人、194 个场景物体、3 辆车；没有 AI 决策、发射子弹或推进世界。查询包含实际子弹的 source/team 排除条件。结果存于 `qa/performance/trace-resource-cost-v32.json`。

360 条 8 米射线合计 **37.303 ms**，其中人体检查 **23.656 ms（63.4%）**，地形 2.651 ms、静态物体 6.200 ms、车辆 4.188 ms。平均每条约 104 μs。初始部署位置并非用户实战位置，因此这个比例不能当作整场 CPU 占比；它证明当前人体候选筛选值得优先重构，并与实战弹道阶段 2.85–5.49 ms 的高开销吻合。

感知和开火还有额外查询：感知刷新筛选最多 10 个目标，每个目标最多两条可见性射线；开火再次确认可见性与可射点，声传播、压制、血滴和弹壳也查询同一几何。单个调用有限并不代表整个显示帧总量小。

## 4. 人物动作跳动：当前视觉调度会随 FPS 下降而降频

角色已经来自原 GLB；CPU 仍通过 AnimationPlayer 采样、调整骨骼/握持、计算命中胶囊，再把姿态送给 GPU 蒙皮。`scripts/proving_ground.gd:847` 给全部 NPC 常规姿态更新共享 **每显示帧 1.8 ms** 预算，屏内目标为 24 Hz，屏外为 6 Hz。

纯资源测试中 60 人完整动作采样 P50 约 **7.70 ms**，平均每人约 0.128 ms。若极端情况下 59 名 NPC 都需更新，24 Hz 约需 181 ms CPU/秒，而 1.8 ms/帧在 60 FPS 时仅提供 108 ms/秒，30 FPS 时仅 54 ms/秒。这个算例不是实际人物刷新率测量，但表明“配置 24 Hz”不能保证在总预算内达到 24 Hz。

当前位置插值只处理根节点；`shaders/crowd_skin.gdshaderinc` 读取一份当前骨骼姿态，没有前后姿态插值。因此低 FPS 下会同时降低姿态更新次数，出现脚步/手臂跳动的风险。开火的 `resolve_muzzle()` 又在物理阶段完整调用 `Motion.update(...,0,...)`，该成本不受 1.8 ms 视觉预算约束。

## 5. 突发卡顿及合批后的剩余工作

- **大范围破坏**：模拟 50.233 s，同帧涉及 59 个墙格，上传 932,256 字节，局部墙更新仍需 **14.539 ms**。43.867 s 的 41 格更新耗时 10.966 ms。单格优化有效，但一帧集中处理整段坍塌仍会造成突刺。
- **特效**：血滴出生时最多 96 次几何追踪；飞行弹壳/弹匣仍由 CPU 积分、检查支撑并上传变换。已经落地的弹壳走休眠分支，不应把它们当成唯一主因。动态批次只解决提交次数，不会自动把这些模拟迁移到 GPU。
- **HUD**：变化数字仍触发文字网格创建/上传。`CombatHUD._draw` 的 last_draw_ms 在没有新绘制时可能保留旧值，其分位数不能当作每帧实际绘制总开销。
- **场景树**：冻结资源共 1416 个 MeshInstance3D，其中 1092 个仅通过 layers=0 排除原绘制；另有 78 套 Skeleton3D/AnimationPlayer（含预热尸体）。合批后仍保留大量节点、骨骼和挂点的更新负担。这是待进一步隔离的引擎侧成本，不能仅凭数量给出毫秒结论。[Godot 场景树成本说明](https://docs.godotengine.org/en/4.6/tutorials/performance/cpu_optimization.html#scenetree)

## 6. 测量边界及下一轮顺序

之前的 `presentation` 计时仅包住主场景 `_process`；虽然记录了子节点 last_ms，但这些值没有计入父回调 elapsed。因此“画面只用 4 ms”是错误解读。`worst_presentation` 也不是最慢的完整显示帧；不能拿它给 58.63 ms 整帧逐项精确归因。

已查到本机为 i5-12400F、6 核 12 线程、RTX 3060。CPU 总占用率低不表示主线程不受限。现有日志没有实战 GPU 时间戳；本轮读取 GPU 利用率时战斗已结束，这个读数不用于排除实战 GPU 瓶颈。原有约 600–730 万图元还含描边、预留/退化三角形，不能直接当作独立模型面数。GPU 仍需单独测时。[Godot 渲染瓶颈说明](https://docs.godotengine.org/en/4.6/tutorials/performance/gpu_optimization.html)

按现有证据，建议后续实现顺序：

1. **优先缩小弹道人体候选集**：专用可持续更新的空间索引，按实际胶囊包围范围登记，子弹只查询穿过的格子；保留原精确胶囊命中、穿透与友伤过滤。补全物理/射线阶段同帧总量记录。
2. **减少重复移动与射击姿态工作**：同一单位同一状态复用查询结果/骨架采样；地形/墙体/车辆变化正确使缓存失效。CPU 继续负责权威命中，GPU 负责连续视觉插值，保留原 GLB 骨架和动作。
3. **将非玩法的特效运动更多交给 GPU**，出生/落点及必要遮挡仍由 CPU 有界处理；静止污迹和 HUD 未变几何不重复上传。
4. **处理大范围破坏突刺**：进一步缓存墙格拓扑、合并连续上传和减少临时数组；若延后视觉工作，必须先保证实际碰撞/弹道破坏立即生效，并明确可接受的视觉延迟。

第一阶段目标应是先让 60 人战斗的单次物理 P95 明显低于当前 11–14 ms，为显示留出余量；之后用逐帧 CPU/GPU 计时和用户实战 P95/P99 验证稳定 60 FPS。不能只靠“Draw Call <50”或菜单帧率宣告完成。
