# Loading and user-play telemetry recovery

- `CampaignLoading` is an independent CanvasLayer. Startup and campaign entry present it before world reconstruction (a real `frame_post_draw` on graphical displays, a process-frame-only fallback in headless contracts). Campaign repeated clicks are ignored. The previous complete world and stage stay frozen until commit; cancellation, explicit placement failure and the 120-second watchdog roll back to them. Chapter selection is saved only after successful reconstruction. Errors expose retry/home/exit.
- Object, vehicle and soldier view loops yield after approximately 6 ms of work. Counters report completed entities, never a fabricated percentage. Individual entity construction, world setup/terrain preparation, terrain mesh and batch configuration are still atomic. Their stage names explicitly say so. This does not establish that the whole five-second stall has disappeared.
- The partial stage has processing disabled; parent physics, presentation and input cannot run until `world_ready`. The world is created lazily at setup. Existing synchronous editor/LAN rebuild calls retain their synchronous behavior; startup uses the loading canvas too.
- Ordinary menu recording calls `set_play_recording`; default is off and independent of the Debug drawer. Repeated enable is idempotent. A real new start creates `user://runtime-performance.jsonl`, up to 8 MiB, with at most 4096 samples per series per report. Stop, exit, rebuild and loading boundaries flush. A new session may replace the previous log; simply closing/reopening Debug cannot.
- Physics, catch-up step count/cost, frame interval, parent presentation, render/FX substages, AI budget and nested diagnostic metadata are retained. Unsupported/zero GPU measurements are reported as unknown, not zero-cost GPU. Boundary clocks and pending physics reset to avoid attributing a load/pause gap to combat.
- `qa/loading_telemetry_contract.gd` tests startup/entry freeze, cancellation/rollback, duplicate entry, injected failure, bounded timeout, retry, full view counts, independent recording, idempotent start, nested metadata and memory caps. These are frozen state contracts, not automated combat or a live FPS claim.

## Verified recovery checkpoint

Godot 4.6.3 headless editor import/parse exited 0. The frozen state contract exited 0 with no failures, all 60 first-chapter soldiers and simulation time 0. This verifies actual instantiated controls and state transitions, not graphical presentation or live combat. The current executor has no DISPLAY/Xvfb, so real presentation is pending graphical validation; headless `drawn` is explicitly false. On this executor the initial world and terrain-mesh atomic stages each took about 10–12 seconds during the campaign retry. That is diagnostic evidence of remaining atomic work, not a user-machine performance measurement.

Startup failure has no previous complete world or menu to restore. Its unavailable Home button is hidden, and the stable error/cancel page offers explicitly named “重新加载场景” and Exit; no automatic reload loop is used. Ordinary campaign entry still restores the previous complete scene and Home. Loading content uses viewport width minus 32 px (maximum 520), wrapping labels and bounded button widths for narrow windows.

Rollback additionally restores the old physics tick rate, jitter fix and max catch-up steps, UI processing mode, editor/style button visibility, and rebinds campaign presentation/equipment/objective controls to the restored world. A training-to-campaign failure is injected after world setup has changed physics policy, then checked for full restoration without advancing simulation or saving chapter progress.
