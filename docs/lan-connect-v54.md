# v2026.09.30.54 加入阻塞与 UDP 端点修复

这些修复在 v54 工作树实施；并行项目工作已将唯一构建版本递增至 **v2026.09.30.55**，最终发行包随统一版本为 v55。

## 现场证据

用户 v53 验收窗口 PID 9128 在“正在连接 192.168.23.181:27829”时显示未响应。该窗口后来转为联合演武场标题，主线程仍消耗 CPU；发行版普通打印日志为空。原加入路径先同步重建第一关，等待默认 ENet 超时，失败又在网络信号回调内重建演武场。

2026-09-30 首次房间查询确认房主版本也是 v53，UDP 27830 正常回复。独立 ENet 直连 27829 无法建立连接；经独立 Python IPv4 数据报转发可以建立。随后用游戏内 `PacketPeerUDP` 转发复现：数据报来源 IP 是 192.168.23.181，回复来源端口却不是原目标 27829。限制目标端口会丢掉所有收到的包；只接受目标 IP，并将回复转回 ENet 预期的本地端点后，独立握手立即成功。当前机器有以太网 192.168.22.23 和 xray_tun 172.18.0.1；已证明发送路径有端口改写，尚未证明是哪个中间组件造成。

早期 Python 远端转发试验错误地绑定 loopback 出口，报 WinError 10051；该失败不作为链路证据。修正为 IPv4 wildcard 出口后，试验正常并完成握手。

后续复测时房主连 27830 查询也停止回复；此时无法据“无回复”判断代码是否有问题。不能把独立传输握手成功等同完整跨电脑战役加入成功。

## 修复

1. `lan_ipv4_transport.gd` 在游戏内转发不修改内容的 ENet 数据报。一个 loopback Socket 对 ENet 呈现稳定端点，一个 IPv4 Socket 连接指定房主。只接收选定房主 IP、指定本地客户端端口的包；每帧每方向最多 256 个，接收缓冲 1 MiB。回复端口允许中间路径改写，ENet 本身仍校验协议包。直接 LAN IPv4 加入启用它，loopback 保留原路径；不改系统路由、VPN 设置或使用外部程序。
2. 连接分为探测、准备、正式连接、战役握手。先用无战役 RPC 的 ENet 连接确认端口可达，再关闭探测、离线准备第一关，随后正式连接。这样不为不可达房主重建关卡，又不在连接已建立时停掉 ENet 轮询数秒加载场景。
3. 连接中不模拟本地 AI 战役；同一连接进行中重复点击不会重启流程。端口无回复 8 秒结束，战役握手 20 秒超时。超时保留现有场景并显示可操作菜单，不再同步重建演武场。
4. 加入快照及断线处理移出网络回调；加载前呈现状态，检查连接尝试序号，取消的旧回调不能重新接管新连接。关闭 ENet 后先将最后的断线包转出，再关闭 IPv4 通道。
5. 连接各阶段及发送 / 接收计数写入 `user://lan-connection.log`，发行版也可诊断。
6. 保留 v53 的实时同步、预测和快照确认；v53/v54 可使用同一实时协议，旧 v45–v52 保留旧协议。
7. 安装包附带用户主动运行的 `允许局域网联机.cmd`。它通过 Windows 管理员提示，仅允许同目录游戏接收 UDP 27829 / 27830，来源限制私有地址范围，保留系统防火墙。迁移目录后需重新运行；不在游戏启动时静默改变防火墙。

## 验证入口

- `qa/lan_connection_trace.gd -- --trace-address=127.0.0.1:27849`：不可达端口 8 秒超时，世界时间不推进，保持原场景并返回菜单。
- `qa/lan_ipv4_contract.gd`：从与目标不同的端口回复，接收后端点正常化，关闭后可重新绑定本地端口。
- `qa/lan_join_smoke.gd`：双进程进行中加入、破坏、姿态、移动与射击。
- `qa/lan_transport_probe.gd -- --native-ipv4`：独立 IPv4 ENet 握手，不代表完整战役加入。

正常验收入口仍为 `res://proving_ground.tscn`，继续复用同一首页和战役。

最终双进程回归 `qa/lan-v54-validated-*.log` 使用修改版客户端与冻结 v53 房主，成功接管 17 号蓝军，破坏修订 2、姿态 1、移动 1.915 m、20 次权威射击、434 个运动分包，房主最大数据报 1032 B。IPv4 端口改写合同测试通过；8 秒失败返回测试通过。最终实际跨电脑战役复测仍取决于房主重新开放房间。
